我同意这个方向。**现在已经证明模型能理解一个成功片段并输出 JSON；下一步要证明它能在执行过程中，及时且可靠地判断完成或失败。**根据你提供的描述，这次完成判断合理，但还不能代表整体准确率。
我建议按下面顺序推进：
1. 先做“视频前缀评测”，最重要
不要每次给完整 episode。按时间逐步提供：
输入范围	期望行为
开始到接近移液器	in_progress
开始到右手接触物体	不能仅凭接触判定完成
开始到物体离开支架	检查是否仍被稳定持有
完成条件持续满足	completed


每次判断只能看到当前及过去的画面。这样才能测出是否提前宣布完成、真正完成后多久才能识别，而不只是事后总结视频。
2. 把五类任务写成“可检查的条件”
每个任务配置：阶段、成功条件、明确失败条件、允许转移、超时条件。
例如取移液器：
- 完成：目标物体离开支架，并由右手持续持有。
- 失败：明确看到物体掉落，或取错物体。
- 不确定：手部遮挡，无法确认是否持有。
- 仍在执行：正在尝试抓取，尚未出现完成证据。
**“还没成功”不能直接等于“失败”。**超时多久、稳定持有多久，应通过样本确定，不先随意写死。
3. 让 JSON 支持外层验证
在现有字段上，优先增加这几个：
{
  "episode_id": "example_001",
  "observation_end_s": 3.2,
  "phase": "lifting",
  "status": "in_progress",
  "conditions": {
    "object_clear_of_rack": true,
    "held_by_right_hand": true,
    "stable_hold_verified": null
  },
  "evidence_frame_ids": [24, 28]
}

null 表示无法确认。这些条件仍是模型预测，但比一段自然语言解释更容易检查、统计和接入状态机。普通轮询保持输出简短，发现异常时再生成详细错误报告。
4. 把 episode 管理与任务进度分开
建议区分两层：
- Episode 层：管理当前片段的帧、时间戳和请求历史。
- 任务链层：管理五步任务的阶段、已验证条件和物体状态。
新片段开始时清空片段缓存；只有确认属于同一任务链，才继承相关任务状态，并用初始观测复核。上一阶段完成，也不自动意味着下一阶段已经开始。
5. 建立一个小型人工标注测试集
先选五类任务各几段，人工标出“完成条件首次满足的时间”和关键证据。补充失败、遮挡、停滞等情况；只有成功片段无法评估失败召回率。
优先记录：
维度	指标
是否乱报完成	提前完成率 / 完成判定 Precision
是否漏掉失败	失败 Recall、误报警率
判断是否及时	完成与失败的检测延迟
系统是否够快	图像采集到结果返回的 P50/P95 延迟


截断成功视频可以测试“未完成”，但不能一律标成失败。
6. 有了基线，再优化速度和闭环
固定同一批测试片段，比较：
单帧 → 短历史 → 阶段锚点＋短历史 → 加状态转移验证。
先确定哪些机制提高准确率，再优化分辨率、帧数、输出长度和缓存。接入 FC 时，先让 critic 只记录建议、暂不影响执行，核对可靠性后再启用阶段切换、重试和停止。
**最近一轮最值得交付的三个东西：五任务判据配置、视频前缀评测脚本、带人工真值的结果表。**这会比继续加泛用 skill 或复杂 agent 模块，更直接地推进项目。
